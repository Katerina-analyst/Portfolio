# Перечень нефункциональных требований

## NFR-01. Удобство использования

| **ID** | **Требование** |
|---|---|
| NFR-01.01 | Названия элементов интерфейса не должны содержать названия таблиц и полей БД, внутренние коды статусов и названия API-параметров |
| NFR-01.02 | Если посетитель при записи не заполнил поля имени или номера телефона либо заполнил их некорректно, система должна отображать сообщение с описанием ошибки и подсказкой по ее исправлению |
| NFR-01.03 | Пользователь должен иметь возможность записаться на одну процедуру не более чем за 9 кликов без учета возвратов к предыдущим шагам и изменения выбранных данных. Подсчет начинается с момента инициирования перехода к форме онлайн-записи и заканчивается подтверждением записи |
| NFR-01.04 | Не менее 90% новых пользователей должны самостоятельно оформлять запись на одну процедуру не более чем за 60 секунд с момента инициирования перехода к форме онлайн-записи и заканчивается подтверждением записи |
| NFR-01.05 | Размер области нажатия интерактивных элементов, используемых на мобильных устройствах, должен составлять не менее 44 × 44 CSS-пикселей |

## NFR-02. Производительность

| **ID** | **Требование** |
|---|---|
| NFR-02.01 | Время отображения основного содержимого лендинга Beauty Bliss, измеряемое по метрике LCP, не должно превышать 2,5 секунды для 75% загрузок страницы при нагрузке до 10 одновременно активных пользователей |
| NFR-02.02 | Время с момента инициирования перехода к форме онлайн-записи до отображения формы с загруженными категориями и процедурами не должно превышать 2 секунд для 95% выполнений операции при нагрузке публичного API до 1 RPS |
| NFR-02.03 | Время с момента инициирования перехода к выбору даты визита до отображения календаря с доступными датами с учетом суммарной длительности выбранных процедур не должно превышать 2 секунд для 95% выполнений операции при нагрузке публичного API до 1 RPS |
| NFR-02.04 | Время с момента выбора даты до отображения свободных временных интервалов с учетом суммарной длительности выбранных процедур не должно превышать 2 секунд для 95% выполнений операции при нагрузке публичного API до 1 RPS |
| NFR-02.05 | Время с момента подтверждения записи клиентом до отображения результата создания записи не должно превышать 2 секунд для 95% выполнений операции при нагрузке публичного API до 1 RPS |
| NFR-02.06 | Публичный API должен обеспечивать обработку смешанной нагрузки не менее 1 RPS в течение 30 минут с соблюдением NFR-02.02–NFR-02.05. При кратковременном увеличении нагрузки до 5 RPS продолжительностью до 60 секунд система должна сохранять целостность данных и не допускать неконтролируемого завершения работы. При превышении гарантированной пропускной способности допускается увеличение времени отклика и контролируемое отклонение новых запросов |

## NFR-03. Надежность и устойчивость

| **ID** | **Требование** |
|---|---|
| NFR-03.01 | Сервис онлайн-записи должен быть доступен не менее 99% времени в течение календарного месяца, включая периоды плановых технических работ. Недоступностью считается невозможность создания записи вследствие технического сбоя системы или проведения технических работ |
| NFR-03.02 | Недоступность сервиса отправки уведомлений не должна приводить к отказу создания, отмены или изменения статуса записи |
| NFR-03.03 | При аварийном завершении backend система должна автоматически восстанавливать его работоспособность в течение 5 минут без ручного вмешательства |
| NFR-03.04 | Время восстановления работоспособности сервиса онлайн-записи после обнаружения критического сбоя, требующего ручного вмешательства, не должно превышать 30 минут с момента уведомления разработчика в рабочие часы (с 09:00 до 21:00). При возникновении сбоя в нерабочее время устранение аварии переносится на ближайший рабочий интервал |
| NFR-03.05 | Сбои фоновых процессов, не участвующих непосредственно в создании и отмене записей, не должны приводить к недоступности сервиса онлайн-записи |

## NFR-04. Целостность и сохранность данных

| **ID** | **Требование** |
|---|---|
| NFR-04.01 | Операция создания записи должна завершаться либо сохранением записи и всех данных, создаваемых в рамках этой операции, либо отсутствием любых изменений |
| NFR-04.02 | Операция отмены записи должна завершаться либо сохранением статуса `canceled` и даты и времени отмены, либо отсутствием любых изменений |
| NFR-04.03 | При одновременных запросах на создание записей система должна исключать создание активных записей с пересекающимися временными интервалами |
| NFR-04.04 | При повторном подтверждении записи клиентом во время обработки предыдущего запроса frontend не должен отправлять дополнительный запрос на создание записи |
| NFR-04.05 | Резервное копирование всех данных БД должно выполняться не реже одного раза в час |
| NFR-04.06 | Резервные копии должны храниться в хранилище, отказ которого не приводит к одновременной потере рабочей БД и резервных копий |
| NFR-04.07 | Система должна обеспечивать хранение не менее 24 последних успешно созданных часовых резервных копий и 7 ежедневных резервных копий БД |
| NFR-04.08 | Система должна обеспечивать восстановление всех данных БД из выбранной доступной резервной копии |
| NFR-04.09 | Целевая точка восстановления данных (RPO) при критическом сбое БД не должна превышать 1 часа |

### NFR-05. Логирование ошибок, мониторинг и оповещения

| **ID** | **Требование** |
|---|---|
| NFR-05.01 | Система должна фиксировать в backend-логах технические ошибки, возникшие при выполнении операций с записями, авторизации косметолога, обращении к БД и взаимодействии с внешними сервисами |
| NFR-05.02 | Каждая запись об ошибке в backend-логах должна содержать дату и время события, уровень логирования, описание ошибки и идентификатор HTTP-запроса, если ошибка возникла при его обработке |
| NFR-05.03 | При ошибке отправки SMS система должна фиксировать в backend-логах идентификатор уведомления, идентификатор записи, SMS-провайдера, а также код и текст ошибки провайдера при их наличии |
| NFR-05.04 | Backend-логи не должны содержать пароль косметолога, refresh-токен, JWT-токен, полные значения номера телефона, email и токена доступа к записи |
| NFR-05.05 | Система мониторинга должна автоматически проверять доступность backend и БД с интервалом не более 1 минуты |
| NFR-05.06 | Система мониторинга должна фиксировать дату и время обнаружения недоступности backend или БД, а также дату и время восстановления их работоспособности |
| **ID** | **Требование** |
|---|---|
| NFR-05.07 | При обнаружении недоступности backend или БД система мониторинга должна автоматически формировать критический алерт и отправлять уведомление разработчику в течение 5 минут с момента обнаружения сбоя |
| NFR-05.08 | Критический алерт должен содержать название недоступного компонента, дату и время обнаружения сбоя и описание выявленной проблемы |
| NFR-05.09 | Система мониторинга должна фиксировать дату и время создания алерта, отправки уведомления и результат отправки |
| NFR-05.10 | Backend-логи должны храниться не менее 30 календарных дней и быть доступны разработчику для анализа технических ошибок |
| NFR-05.11 | После восстановления работоспособности компонента система мониторинга должна автоматически переводить соответствующий алерт в состояние "Закрыт", фиксировать дату и время закрытия и отправлять разработчику уведомление о восстановлении |
| NFR-05.12 | Система должна фиксировать в журнале безопасности успешные и неуспешные попытки аутентификации косметолога, выход из учетной записи и отказы в доступе к защищенным ресурсам |
| NFR-05.13 | Каждая запись журнала безопасности должна содержать дату и время события, тип события, результат операции и идентификатор пользователя при его наличии |

### NFR-06. Безопасность системы

| **ID** | **Требование** |
|---|---|
| NFR-06.01 | Доступ к личному кабинету и функциям управления профилем, процедурами, расписанием и записями должен предоставляться только успешно аутентифицированному косметологу |
*| NFR-06.02 | При выходе косметолога frontend должен удалять JWT из оперативной памяти, а backend - отправлять ответ с удалением cookie, содержащей refresh token |* - переделать?
| NFR-06.03 | При вводе неправильного логина или пароля система должна отображать общее сообщение об ошибке без указания, какие именно данные введены неверно |
| NFR-06.04 | Все защищенные REST API-методы должны принимать JWT в заголовке `Authorization` по схеме `Bearer`. JWT должен храниться в оперативной памяти frontend-приложения |
| NFR-06.05 | Система должна ограничивать количество запросов к защищенным REST API-методам от одного авторизованного пользователя до 20 запросов в минуту |
| NFR-06.06 | Система должна ограничивать количество запросов к публичным REST API-методам от одного IP-адреса до 60 запросов в минуту |
| NFR-06.07 | Система должна ограничивать количество запросов на создание записи от одного IP-адреса до 5 запросов в минуту |
| NFR-06.08 | Срок действия JWT косметолога должен составлять 15 минут с момента его выдачи |
| NFR-06.09 | Срок действия refresh token косметолога должен составлять 30 календарных дней с момента его выдачи |
| NFR-06.10 | Refresh token должен храниться на клиенте и передаваться серверу в cookie с атрибутами `HttpOnly`, `Secure` и `SameSite`, значение которого соответствует схеме взаимодействия frontend и backend |
| NFR-06.11 | Backend должен проверять действительность JWT и права доступа косметолога при каждом обращении к защищенным REST API-методам |
| NFR-06.12 | Система должна ограничивать количество неуспешных попыток аутентификации косметолога: не более 3 попыток для одной учетной записи в течение 15 минут. При превышении лимита дальнейшие попытки должны блокироваться на 60 минут |
| NFR-06.13 | При превышении установленного лимита запросов REST API должен возвращать HTTP 429 и не выполнять запрошенную операцию |
*| NFR-06.14 | При обновлении JWT backend должен проверять подпись и срок действия refresh token. При недействительном или просроченном токене новый JWT не должен выдаваться |* - переделать?
| NFR-06.15 | При отсутствии, истечении срока действия или недействительности JWT защищенные REST API-методы должны возвращать HTTP 401 и не выполнять запрошенную операцию |
| NFR-06.16 | При отсутствии у аутентифицированного пользователя прав на запрошенную операцию REST API должен возвращать HTTP 403 и не выполнять операцию |
| NFR-06.17 | При установке или изменении пароля косметолога система должна принимать пароль длиной от 15 до 64 символов включительно |
| NFR-06.18 | Пароль косметолога должен храниться в виде хеша, сформированного алгоритмом, предназначенным для хранения паролей, с уникальной солью |
| NFR-06.19 | Доступ к персональным данным клиентов должен предоставляться авторизованному косметологу, а клиенту - только к данным собственной записи по действительному уникальному токену доступа. Проверка прав доступа должна выполняться на backend |
| NFR-06.20 | Весь обмен данными между браузером пользователя и REST API должен выполняться только по защищенному соединению HTTPS |
| NFR-06.21 | База данных, используемая для хранения персональных данных клиентов, должна находиться на территории Российской Федерации |
| NFR-06.22 | Доступ к резервным копиям БД, содержащим персональные данные клиентов, должен предоставляться только уполномоченным лицам |
| NFR-06.23 | Резервные копии БД, содержащие персональные данные клиентов, должны храниться в зашифрованном виде |
| NFR-06.24 | Токен доступа к записи клиента не должен включаться в ответы REST API, за исключением операций, для которых выдача этого токена необходима |
| NFR-06.25 | Перед публикацией новой версии backend и frontend должна выполняться автоматизированная проверка программных зависимостей на наличие известных уязвимостей высокого и критического уровня опасности |
| NFR-06.26 | Публикация новой версии системы с обнаруженными уязвимостями высокого или критического уровня опасности допускается только после их устранения либо документированного согласования выявленных рисков с ответственным за систему |

### NFR-07.Совместимость

| **ID** | **Требование** |
|---|---|
| NFR-07.01 | Интерфейс публичной части сайта должен корректно отображаться на мобильных устройствах, планшетах и десктопах без горизонтальной прокрутки страницы, перекрытия элементов управления и обрезания текста, необходимого для выполнения пользовательского сценария |
| NFR-07.02 | Клиент должен иметь возможность полностью выполнять основные сценарии публичной части сайта на мобильном устройстве |
| NFR-07.03 | Основные пользовательские сценарии должны выполняться без ошибок, препятствующих завершению сценария, в текущей стабильной и предыдущей стабильной версиях браузеров Chrome, Safari, Firefox, Yandex и Edge |
